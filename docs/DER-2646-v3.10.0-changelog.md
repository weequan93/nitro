## Summary

This release combines the DER execution blacklist, gasless transaction gas
estimation, state-backed ArbSys route governance, exact-route enforcement for
ERC-20 withdrawals and arbitrary messages, the DeriwOS 3 direct native-ETH
withdrawal exception, DeriwOS 5 subaccount authorization hardening, published
submodule revisions, and deployment/governance tooling.

Deriw-specific consensus changes are independently versioned from upstream
ArbOS. Internal ArbOS remains version 60 (`ArbSys.arbOSVersion()` reports 115),
while DeriwOS selects the active DER behavior:

| DeriwOS | Behavior |
|---|---|
| 0 | Historical behavior |
| 1 | Consensus execution blacklist |
| 2 | State-backed exact-route enforcement for ArbSys outbound sends |
| 3 | Direct `withdrawEth(address)` allowed; raw `sendTxToL1` and ERC-20 gateway sends remain route-restricted |
| 4 | Future DeriwOS scheduling is chain-owner-only through `ArbOwner`; the legacy blacklist scheduler cannot schedule version 4+ |
| 5 | Strict, timestamp-bounded subaccount authorization plus consistent one-to-one parent/child updates |

The version transition is state-backed and timestamp-scheduled. Nodes reject
active DeriwOS versions newer than the binary supports.

## Added

### Independent DeriwOS lifecycle

- Added append-only ArbOS state for the active DeriwOS version, pending target,
  activation timestamp, and the ArbOS version recorded when scheduled.
- Added canonical chain-owner-only scheduling and cancellation through
  `ArbOwner` at `0x0000000000000000000000000000000000000070`.
- Added canonical public version and schedule reads through `ArbOwnerPublic` at
  `0x000000000000000000000000000000000000006B`.
- Retained the old `DeriwBlacklist`/`DeriwBlacklistPublic` selectors for
  historical compatibility. The legacy write endpoint rejects DeriwOS 4+.
- Added startup rejection when chain state requires a newer DeriwOS version
  than the running node supports.
- Preserved historical execution before each version boundary.

### DeriwOS 1: consensus blacklist

- Moved the blacklist security invariant into consensus execution so forced and
  delayed transactions cannot bypass a sequencer-only admission filter.
- Checks the union of the legacy sender and destination lists for each checked
  top-level identity:
  - signed transaction sender;
  - effective parent of a permitted subaccount transaction; and
  - explicit top-level destination.
- Applies the appropriate aliased/original identities to relevant L1-originated
  executions and applies normal checks when a retryable ticket executes.
- Produces a failed receipt on violation, consumes the complete supplied gas
  limit without refund, preserves no user execution effects, and advances the
  applicable signed-child/effective-parent nonces.
- Retains admission filtering to reject known violations before publication,
  while consensus remains the authoritative enforcement layer.
- Allows funding-only deposits and retryable ticket creation so bridge funds
  remain recoverable.
- Excludes protocol-generated `ArbitrumInternalTx` execution from blacklist
  enforcement.
- Provides a narrow emergency recovery exception for an authorized owner making
  a direct, zero-value, canonical blacklist-removal call.
- Prevents protected system/protocol addresses, the L1 pricing pool, batch
  poster, and current fee accounts from being quarantined once DeriwOS 1 is
  active or scheduled.
- Rejects replacement fee accounts that are already quarantined.

The DeriwOS 1 blacklist is intentionally a top-level transaction policy. It
does not inspect calldata, ERC-20 participants, nested EVM calls, derived
contract addresses, `SELFDESTRUCT` beneficiaries, or arbitrary indirect
interactions.

### DeriwOS 2: state-backed ArbSys route enforcement

- Added state-backed router configuration containing:
  - Deriw router;
  - canonical gateway router;
  - complete approved token-gateway list; and
  - monotonically increasing configuration revision.
- Added chain-specific compiled bootstrap routes for dev, test, and production.
- Added chain-owner methods to stage, read, activate, replace, and cancel a
  router configuration using a future activation timestamp.
- Fails closed when no valid active route exists or an unknown token gateway is
  used.
- Enforces exact normalized route suffixes:
  - direct router route: `[Deriw router]`;
  - ERC-20 route: `[Deriw router, canonical gateway router, approved gateway]`.
- Ignores only `DELEGATECALL`/`CALLCODE` implementation frames during
  normalization, retains ordinary duplicate frames, requires protected route
  addresses to occur exactly once, and requires the final normalized frame to
  agree with the immediate precompile caller.
- Places route enforcement before outbound-send state access and mutation.
- Covers both direct `sendTxToL1` calls and gateway-originated canonical ERC-20
  sends.

### DeriwOS 3: direct native-ETH withdrawal

- Added an explicit operation type inside `ArbSys` so authorization depends on
  the ABI entry point, not on ETH value or empty calldata.
- Exempted only the real `withdrawEth(address)` entry point from the route guard.
- Continued to enforce the DeriwOS 2 route policy for:
  - raw `sendTxToL1(address,bytes)`;
  - raw calls carrying ETH with empty calldata;
  - canonical ERC-20 gateway sends; and
  - unknown operations, which fail closed.
- Kept the DeriwOS 2 behavior unchanged until the separately scheduled
  DeriwOS 3 activation boundary.

### DeriwOS 5: subaccount authorization hardening

- Preserves the historical subaccount authorization and relationship behavior
  through DeriwOS 4 so pre-activation blocks replay identically.
- At DeriwOS 5, requires the exact EIP-712 domain and Grant/Revoke message
  schemas, the expected domain name/version, and the `0x07E9` verifying
  contract. Unknown JSON fields and noncanonical timestamps are rejected.
- Accepts authorizations no more than 600 seconds old and no more than 30
  seconds in the future, using the L3 block timestamp.
- Keys Grant and Revoke replay protection by the verified EIP-712 digest and
  signer, while recognizing legacy Grant signature keys across both recovery
  byte encodings.
- Makes parent/child rebinding and revocation consistent in both maps and makes
  position-based administrative cleanup remove matching counterpart entries.
- Keeps `chainId` in the signed EIP-712 domain for client compatibility but
  deliberately does not compare it with the node chain ID. No signed nonce is
  introduced in this compatibility release.

### Gasless `eth_estimateGas`

- Added an RPC hook that asks ArbOS whether the transaction destination is on
  the gasless/custom-price target allowlist.
- Normalizes legacy and EIP-1559 fee fields to zero during gas estimation for an
  allowlisted target, preventing a sender's native balance from incorrectly
  capping or rejecting the simulation.
- Handles omitted, zero, and nonzero fee-field combinations consistently.
- Keeps non-allowlisted estimation behavior unchanged.
- Uses the destination allowlist only; sender-only allowlisting does not make an
  arbitrary destination gasless during estimation.

### Governance and deployment tooling

- Added a dev/test/prod L3 deployment runbook with separate parent-contract,
  WASM-root, node-rollout, route-configuration, and DeriwOS activation waves.
- Documented the approved governance path as Safe to UpgradeExecutor to target;
  deployment instructions do not use a direct privileged EOA call.
- Added a development L3 governance-migration audit/verification script.
- Added a Safe proposal tool that validates chain-specific UpgradeExecutor
  targets, rejects direct governance targets and `DELEGATECALL`, validates
  prepared proposal manifests, and requires explicit acknowledgement for
  batches.
- Hardened WASM-root validation to fail on missing directories, prover,
  machine, or module-root artifacts; it now prints each verified root.
- Added the previous accepted DeriwOS machine
  (`0xd37b89a0...6167f4d`) and the current development machine
  (`0x92f0edc3...d1071a7`) to the Docker image so rolling upgrades can retain
  the old root while selecting and validating the new root.
- Added explorer ABI updates for DeriwOS and router-configuration methods.

## Changed

- Updated the blacklist pre-checker to resolve and check the effective
  subaccount parent consistently with consensus behavior.
- Added deterministic full-gas accounting for Deriw blacklist failed no-ops in
  the `go-ethereum` state transition.
- Added a distinct `ErrDeriwBlacklisted` VM error and error code.
- Refactored `ArbSys.SendTxToL1` and `ArbSys.WithdrawEth` through one shared
  implementation while retaining the original operation identity.
- Published the consolidated submodule revisions instead of relying on local,
  unreachable commits.
- Expanded release precautions, security findings, route-management guidance,

## Compatibility and operator action

- This is a consensus and validator-machine release. Every node role that may
  validate post-activation blocks must run a binary supporting DeriwOS 5 and
  have the required machine artifacts before activation.
- Do not activate behavior before the parent Rollup accepts the matching WASM
  module root and validators have completed pending-root validation.
- Keep current and pending machines available during rolling upgrades.
- Test and production require their own address verification, Safe proposal,
  parent-root update, observation window, and separately scheduled DeriwOS
  transitions.
- Router configuration changes are on-chain governance changes; changing a
  hardcoded bootstrap value alone does not modify an already activated route.

## Known limitations and security assumptions

- Exact route enforcement proves the outbound call path, not the original
  user's authorization. Router caller/signature checks remain required.
- The Deriw router and canonical gateways are upgradeable. Their administrators
  and implementation security remain in the trusted computing base unless code
  or implementation hashes are pinned.
- The router must retain one shared outbound reentrancy guard and must not expose
  user-controlled arbitrary execution or `DELEGATECALL`.
- Direct native-ETH withdrawal is intentionally permissionless at DeriwOS 3.
  Raw arbitrary messages and ERC-20 gateway sends are not permissionless.
- Canonical recovery sends whose stack does not contain the approved Deriw route
  remain blocked and require an explicitly designed route or accepted recovery
  procedure.
- DeriwOS 4 and later scheduling is contractually restricted to chain owners by
  the `ArbOwner` wrapper. The release runbook additionally requires an approved
  Safe → UpgradeExecutor → ArbOwner path.
- DeriwOS 5 does not add a signed nonce and does not enforce the signed EIP-712
  `chainId`. Its replay boundary is the signer-scoped digest plus the 10-minute
  validity window and fixed `0x07E9` verifying contract.
- Gasless estimation is destination-based. Sender-only gasless policy is not
  applied by the estimation hook.
- Parent-chain receivers must independently authenticate canonical Outbox
  execution and the recorded L3 sender.
